# Agent Runtime 面试问答稿

> 面向 Agent Infra / Agent 平台类岗位。基于本项目当前代码形态整理。
> 用法：先背"核心答案"，再熟悉"追问应对"。⚠️ 标记处是面试雷区，务必注意措辞。
> 项目双形态：根包（`runtime.go`/`executor.go`/`runtime_test.go`）是内存态机制验证层，
> 用于验证核心语义（CAS、幂等、取消）并承载并发竞态测试；`internal/` 是面向生产的工程实现
> （MySQL 状态真相源、Redis Streams 投递、RocketMQ 事件、Outbox/Inbox、HITL、OTel）。
> 面试时先讲清这个分层，本身就是一个加分的叙事。

---

## 一、项目开场（1 分钟版本）

**Q：介绍一下你这个项目。**

> 我用 Go 从零实现了一个面向生产的 Agent Runtime。它不做具体某个框架或 SDK 的事，
> 而是回答一个问题：**任何 Agent——不管它用什么模型、什么工具协议——怎么可靠地执行**。
>
> 架构分三层：Capability 层用 Provider/Adapter 解耦 LLM、MCP、内部工具等异构能力；
> Execution 层用 Run/Node/Checkpoint/Event 承载可恢复执行；Reliability 层用
> CAS、租约、重试、幂等、Outbox/Inbox 保证崩溃后能从正确状态继续。
>
> 最有意思的部分是可靠性机制：工具幂等不是宣称 exactly-once，而是
> "成功缓存 + 崩溃保守重试"；人工审批是持久化状态而不是内存 channel；
> 事件通过 Outbox 落库再投 MQ，进程崩溃也不会丢。

**设计一句话**：DAG/Planner 决定 *执行什么*，Runtime Kernel 保证 *怎么可靠执行*，两者边界清晰。

## 二、架构设计

**Q：为什么分 Capability / Execution / Reliability 三层？**

> 每层解决一个独立问题，且各自可独立演进：
> - **Capability**：Agent 能调用什么。ModelProvider/ToolProvider/MCPProvider 是稳定端口，
>   具体 SDK（OpenAI、Eino、MCP SDK）是适配器。换能力不动内核。
> - **Execution**：Agent 怎么跑。Run 是顶层生命周期，Node 是最小持久化执行单元，
>   调度/租约/重试/检查点都以 Node 为粒度。
> - **Reliability**：Agent 怎么稳定跑。CAS 管状态一致性，Lease 管崩溃回收，
>   Outbox/Inbox 管事件不丢不重。
>
> 这样避免把任何一个 LLM SDK、Agent 框架或协议耦合进内核——内核只依赖自己的合同
> （`internal/contracts`），这是它能做"通用运行时"的前提。

**Q：RuntimeEvent 是什么，为什么不直接透传 SDK 的事件？**

> RuntimeEvent 是事件的中间表示（IR）：RUN_STARTED / TEXT_DELTA / TOOL_CALL /
> TOOL_RESULT / RUN_COMPLETED 等。所有 LLM/工具/生命周期信号先归一成它，
> 再适配到 SSE、AG-UI、A2A 等上层协议。
> 好处：内核事件语义稳定，上层协议独立演进，SSE/AG-UI 的格式变化不会反向污染内核；
> 同时一条事件流可以同时喂 SSE、MQ、日志和 OTel，不用每个消费方改一遍。
> 另外 token 流是临时的（不落库），持久状态走 Checkpoint——不是每个 token 都要持久化。

## 三、可靠性深挖（面试主战场）

**Q：工具幂等怎么做的？**

> 幂等键是 `sha256(run_id | node_id | tool_name | input)`，工具调用记录持久化在
> `tool_call` 表，状态机 RUNNING → SUCCESS/FAILED：
> - SUCCESS：直接复用持久化结果，绝不重执行
> - FAILED：允许重试
> - RUNNING：副作用状态未知时**拒绝盲目重执行**
>
> ⚠️ 关键表述：这是"成功缓存 + 崩溃保守重试"，**不是** exactly-once。
> 对扣款、发邮件这类非幂等副作用，宁可少执行一次让人工介入，也不能重复执行。

**Q：为什么做不到 exactly-once？**

> 分布式系统的经典窗口：工具执行成功 → 状态落盘前进程崩溃 → 恢复后无法区分
> "没执行"和"执行了但没记录"。此时重执行有重复副作用风险，不重执行可能丢结果。
> 没有事务性副作用存储（如支持事务的外部系统）配合，这个窗口无法消除。
> 所以诚实的答案是 at-least-once 投递 + 幂等键去重，把语义收敛到"成功结果只产生一次"，
> 而不是宣称副作用只发生一次。

**Q：节点完成事件怎么保证不丢？**

> Outbox 模式：节点完成时在**同一个 MySQL 事务**里 `UPDATE node + INSERT outbox_event`，
> 然后由独立的 Outbox Publisher 把事件投到 RocketMQ。
> 因此不存在"节点已完成 → 进程崩溃 → 事件永远丢失"。
> 消费端用 Inbox 表对 MQ 重投去重。事件投递是 at-least-once，Inbox 保证处理幂等。

**Q：worker 崩溃后，卡住的节点谁回收？**

> 租约（Lease）：worker 领取节点时写入租约和过期时间，执行中续约；
> 崩溃后租约过期，recovery 组件扫描 `RUNNING 且租约过期` 的节点，重新置回就绪状态
> 重新投递。幂等键保证重投后不会重复产生副作用。

**Q：状态并发更新怎么防冲突？**

> CAS 乐观锁：所有状态翻转都是"带版本号的原子条件更新"，
> 等价于 `UPDATE ... SET version=version+1 WHERE id=? AND version=?`。
> 冲突时不是简单失败——要么重试（带退避和上限，防活锁），要么按状态语义判定中止。
> 我用并发取消的竞态测试验证过：30 轮随机时机取消，终态只能是 SUCCESS 或 CANCELLED，
> 不允许把版本冲突这类内部错误泄漏给调用方。

**Q：重试为什么用延迟队列而不是 sleep？**

> 如果在 worker 里 `time.Sleep` 等退避，4 个 worker 被失败任务占满就全部停摆。
> 正确做法是失败节点置回就绪并写 `ready_at` 时间戳作为投递闸门，
> 退避时间没到就不投递，不占用任何执行线程。指数退避带抖动防惊群，重试耗尽进 DLQ。

## 四、并发取消（实际踩过坑，重点准备）

**Q：取消一个正在运行的 Agent 怎么实现？**

> 取消是**状态标记**，不是强杀：把 Run 翻到 CancelRequested，主循环和步骤边界
> 检测到后收敛到 Cancelled。三个我实际修过的坑：
>
> 1. **CAS 无重试**：主循环的版本更新一旦冲突就直接退出，恰好被并发取消撞上时，
>    会以裸的版本冲突报错，还留下已创建没人执行的孤儿步骤。
>    修法：版本冲突→重读最新状态→重试，带次数上限防活锁。
> 2. **取消被成功覆盖**：收尾写终态时不做条件检查，时序上取消刚生效、
>    最后一步恰好成功，Success 就把取消意图盖掉了。
>    修法：条件终态转移——Success/Failed 只能从 Running 转，
>    Cancelled 只能从 CancelRequested 转，取消意图永远优先。
> 3. **检查点不累积**：每次快照只写当前一条，把之前的冲掉了，
>    断点恢复时拿不到完整进度。修法：读旧快照、追加、去重。
>
> 这三个都配了竞态测试：随机时机取消压力测试、取消风暴（恰好一个成功）、
> 运行前取消是无害空操作、幂等重投递不重复执行工具。

**Q：为什么不用 context 强杀？**

> context 取消只能中断当前进程内的调用，无法处理"取消请求到达时步骤正在另一个
> 持久化状态里"的情况——比如节点已投递到队列还没被领取，或进程正在重启。
> 状态标记 + 边界检查才能跨越进程边界生效。对运行中的长步骤，
> 可以把 Run 级 context 传给执行器做协作式中断，这是下一步增强。

## 五、如何回应"这是个玩具"——接入场景论证（核心章节）

⚠️ 这是最可能出现的质疑。错误应对是辩解"我的设计很完整"；
正确应对是**主动展示它怎么接进真实系统**——接入场景本身就是"这不是玩具"的证据，
因为玩具没有可接入的边界，只有 demo 才有。

**Q：你这个项目，真实场景能用吗？还是就是个玩具？**

> 我理解这个质疑——它确实没有生产流量，这点我不回避。
> 但我想展示的是：这个 runtime 的设计目标就是**被接入**，它的每个边界都是按
> 真实接入场景画的。我讲三个具体场景。
>
> **场景一：模型和工具协议是可替换的，可靠性机制跟着走。**
> 内核只依赖 `ModelProvider`（Generate/Stream）和 `ToolProvider`（ListTools/CallTool）
> 两个端口。业务从 OpenAI 切到自建 vLLM、或者工具协议从 function-calling 切到 MCP，
> 只需要换 adapter，内核不动一行。关键是：**换完之后，租约回收、幂等保护、崩溃恢复
> 这些可靠性机制对新的模型和工具同样生效**。一个玩具框架做不到这一点，
> 因为它的能力获取和可靠性是焊死的。
>
> **场景二：事件流对接前端和协议生态。**
> 所有执行信号归一成 RuntimeEvent，向下可以适配 SSE 给前端做流式渲染，
> 向上可以适配 AG-UI / A2A 这类 agent 互操作协议，协议演进不反向污染内核。
> 其中 HITL_REQUESTED / WAITING_HUMAN 这类事件，真实业务里对应的就是
> "审批流"——这是每个企业级 agent 落地都绕不开的东西。
>
> **场景三：长任务和人工审批的真实形态。**
> 设想一个跑两小时的客服处理任务：中途发布重启、或 worker 节点被回收，
> 内存态脚本直接丢任务，而这个运行时靠租约 + 检查点 + Outbox 从正确状态继续；
> 执行到"给用户退款"这步，落 WAITING_HUMAN 持久化状态等人工审批，
> 审批系统可能是几小时后才回调——**审批状态不依赖任何进程活着**。
> 这两个性质，是"脚本"和"基础设施"的分界线。
>
> 所以我的定位是：这是一个把分布式可靠执行的语义做对了的 agent 执行内核，
> 缺的是流量和规模验证，不是设计。而补上这两样的路径我也想好了
> （见下条"还缺什么"）。

**Q：那你觉得它还缺什么才能上生产？**

> 三件事，按优先级：
> 1. **混沌验证**：杀 worker、断网、重启进程，量化恢复时长和状态正确性。
>    机制都实现了，缺的是故障注入下的系统性验证。
> 2. **负载与容量**：队列深度、租约超时参数、DLQ 堆积的处理策略，需要压测数据支撑。
> 3. **多租户治理**：表里已经有 tenant 维度，但配额、限流、优先级队列还没做。
>
> ⚠️ 这个回答的要点：把"缺什么"说成"下一步做什么"，是 infra 工程师的思维方式；
> 而把缺点藏起来或含糊带过，反而坐实"玩具"印象。

**Q：为什么用 Go？为什么自己造轮子？**

> Go 的理由：worker/recovery/resume 是大量并发的常驻服务，goroutine 模型、
> 编译部署单二进制、内存占用可控，都适合这类基础设施组件。
> 造轮子的理由：这不是重复造轮子，而是**在轮子该存在的层级补位**——
> 市面框架解决"怎么编排 agent"，这个项目解决"编排出来的东西怎么可靠执行"。
> 而且自己实现一遍，才对租约、幂等、Outbox 这些机制有代码级的理解，
> 这正是 infra 岗位需要的深度。

## 六、与现有方案的差异（必考）

**Q：和 LangGraph / Temporal / Dify 有什么区别？**

> 定位不同，不是同类竞品：
> - **LangGraph** 这类是 agent 编排框架：擅长图结构和状态管理，但状态默认在内存/
>   单进程视角，持久化和分布式恢复不是第一设计目标。
> - **Temporal** 是通用 durable workflow 引擎：可靠性极强，但它不懂 agent 语义——
>   没有工具幂等、没有 HITL、没有事件流、没有 token/cost 追踪，
>   接 agent 场景要写大量胶水。
> - **Dify** 这类是产品化平台：面向应用搭建，运行时细节是黑盒，不可定制。
>
> 这个项目填的是中间空位：**一个理解 agent 语义（工具调用、流式事件、人工审批、
> 对话上下文）的 durable execution 内核**。它可以作为上面任何一类框架的
> 执行底座——框架负责编排逻辑，内核负责可靠执行。

**Q：为什么不直接用 Temporal？**

> 可以用，但要补四样东西：工具幂等键与副作用策略、agent 原生的事件模型、
> HITL 的持久化语义、LLM 特有的计量与降级。这些恰好是这个项目实现的，
> 也说明这个层级确实存在真实需求。而且 Temporal 的 SDK 绑定意味着
> 执行语义要迁就它的编程模型；自建内核可以按 agent 的需要定义合同。

## 七、权衡与边界（展示成熟度）

**Q：MySQL 做状态真相源，性能够吗？**

> 当前规模下够：状态翻转是低频操作（每节点几次），高频的是事件流和任务投递，
> 那两条路走 Redis Streams 和 RocketMQ，不打数据库。
> 瓶颈预期在 run/node 表的写入，届时方案是分库分表（表已带 tenant 维度）
> 或把步骤级状态迁到更快的存储。⚠️ 不要说"MySQL 没问题"，要说"当前瓶颈不在它"。

**Q：为什么事件走 MQ 而不是直接回调？**

> 回调把生产者和消费者焊死：消费者挂了生产者跟着阻塞，且没有重投语义。
> MQ + Outbox/Inbox 换来的是解耦、重投、回溯。代价是端到端延迟从同步变成异步，
> 以及多维护两个组件——这个取舍对"长任务可恢复"这个目标是值得的。

**Q：Checkpoint 和 MySQL 状态，谁是准的？**

> MySQL 状态机是真相源，Checkpoint 是上下文恢复缓存（对话历史、节点输出）。
> Checkpoint 丢了不破坏正确性——最多重新加载上下文；但状态机绝不能只存 Checkpoint。
> 这是"缓存可丢、状态不丢"的经典分层。

## 八、面试雷区清单

⚠️ **不要说 exactly-once**。说"at-least-once 投递 + 幂等键，把语义收敛到
成功结果只产生一次；非幂等副作用靠保守策略避免重复"。

⚠️ **不要说没有缺点**。缺点清单主动说：无生产流量、混沌验证未做、
多租户治理未做、根包内存版与生产版尚未统一为单一部署形态。

⚠️ **不要混淆两层形态**。根包（内存态）是机制验证 + 竞态测试的载体，
`internal/`（MySQL/Redis/RocketMQ）是工程实现。被问"你跑过吗"时：
机制层有竞态测试验证，工程层 `go build ./... && go vet ./...` 全量通过，
端到端联调（docker compose 起基础设施）是下一步。⚠️ 不要把没跑通的模块说成已验证。

⚠️ **不要把"取消"说成杀进程**。取消是状态标记 + 边界检查，
能跨进程边界生效，这是设计决策不是实现局限。

⚠️ **被问没答上来的，承认 + 给方向**。比如"多实例竞争领取"没做过压测，
就说"租约语义已实现，多实例竞争行为我预期靠数据库行锁 + 版本号兜底，
但需要压测确认，这是混沌验证的一部分"。

## 九、高频快问快答

| 问题 | 要点 |
|---|---|
| 幂等键怎么设计 | `sha256(run_id\|node_id\|tool_name\|input)`，RUNNING 态保守拒重执行 |
| 为什么不是 exactly-once | 成功→落盘之间的崩溃窗口无法消除；诚实语义是 at-least-once+去重 |
| 事件怎么不丢 | Outbox：状态更新与事件落库同事务，Publisher 持续投递 |
| MQ 重投怎么办 | Inbox 表去重，处理幂等 |
| 崩溃节点谁回收 | 租约过期扫描 + 重投递，幂等键防重复副作用 |
| 重试为什么不影响吞吐 | 失败置回就绪 + `ready_at` 闸门，不占执行线程，不是 sleep |
| 退避策略 | 指数退避 + 抖动防惊群，耗尽进 DLQ |
| 取消怎么实现 | 状态标记 + 边界检查；取消优先于成功写终态（条件转移） |
| 并发冲突怎么防 | CAS 乐观锁，冲突重试带上限；不泄漏内部错误给调用方 |
| 人工审批怎么跨重启 | WAITING_HUMAN 是持久化状态 + run_interrupt 记录，不依赖内存 channel |
| Checkpoint 存什么 | 对话历史、节点输入输出；是缓存不是真相源，丢了不破坏正确性 |
| 换模型要改内核吗 | 不要，换 ModelProvider 的 adapter；可靠性机制对新能力同样生效 |
| 事件怎么到前端 | RuntimeEvent IR → SSE/AG-UI/A2A 适配器，协议演进不污染内核 |
| 怎么观测 | OpenTelemetry：Run→Worker→Executor→LLM/Tool→Resume 全链路，带 token/cost 属性 |
| 和 Temporal 关系 | 定位互补：它是不懂 agent 语义的通用引擎，本项目是 agent 原生的执行内核 |
| 测试怎么做的 | 根包竞态测试：随机时机取消、取消风暴、幂等重投递、多 Run 并发，建议 `-race` 跑 |
